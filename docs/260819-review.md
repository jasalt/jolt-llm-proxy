## Architecture assessment

The project has a sound “functional core, imperative shell” shape:

```text
codex.core
  ├─ codex.cli
  └─ codex.proxy
       ├─ codex.schema / codex.translate
       ├─ codex.transport.sse
       ├─ codex.transport.ws
       │    ├─ codex.ws
       │    └─ codex.continuation
       └─ codex.collect
```

Strong points:

- One lifecycle owner in `codex.core`.
- Runtime dependencies passed through a handler closure.
- Ring boundary separated from transport and collection.
- String-keyed validation before normalization.
- Pure continuation logic.
- Common event-source interface (`:read`, `:finalize`) keeps SSE and WS interchangeable.
- Exact dependency pinning and deterministic tests.
- Jolt-specific FFI/tagged-table details are confined mainly to `codex.ws` and `codex.auth`.

No framework-scale redesign is warranted.

### Remaining architectural pressure points

1. **`codex.ws` has two distinct responsibilities**
   - RFC 6455 framing/handshake/connection handling.
   - Session-pool lifecycle and continuation storage.

   At 453 lines, it is the clearest future split:

   ```text
   codex.ws.frame
   codex.ws.connection
   codex.ws.pool
   ```

   This would especially help test frame parsing without constructing connection maps.

2. **The WS implementation has almost no direct automated coverage**

   `codex.ws` is the largest and most protocol-sensitive namespace, but no `ws_test.clj` is registered. High-value cases remain:

   - payload lengths 125/126/65535/65536;
   - partial reads;
   - fragmentation and aggregate limits;
   - ping/pong/close;
   - malformed control frames;
   - simultaneous acquire/release;
   - idle expiry and stale releasers.

3. **Runtime isolation is slightly incomplete**

   `codex.core` creates an isolated pool atom, but `codex.ws/pool` remains as unused global state and `pool-lock` is global. Separate application instances therefore have isolated data but serialize pool operations through the same lock.

   A future pool resource could be:

   ```clojure
   {:sessions (atom {})
    :lock     (Object.)}
   ```

4. **Error handling is the most important remaining cross-cutting concern**

   `codex.proxy` duplicates exception handling and sometimes exposes raw exception messages. `open-event-source` catches every throwable and falls back to SSE, including errors that may not be transport-specific.

   A small internal taxonomy would improve this more than a routing framework:

   ```clojure
   {:type :input}
   {:type :auth}
   {:type :upstream-http}
   {:type :upstream-protocol}
   {:type :timeout}
   {:type :internal}
   ```

   One Ring error mapper could then assign status, public message, error code, and log level.

5. **Dependency injection does not yet cover time, random, and all HTTP calls**

   Direct `System/currentTimeMillis`, `SecureRandom`, and `http/get`/`http/post` calls appear across authentication, CLI, collectors, WS pooling, and model responses. Small function dependencies would improve deterministic testing:

   ```clojure
   {:now-ms     #(System/currentTimeMillis)
    :random     ...
    :http-post  ...
    :http-get   ...}
   ```

6. **Collectors are state-confined but not pure**

   `codex.collect` describes pure reducers, but its accumulators contain mutable `StringBuilder`s. This is safe while each collector remains single-thread-owned, but maps can change without an explicit map transition. Immutable strings or explicitly documented mutable builders would make the contract clearer.

7. **`codex.cli` is the next likely namespace to split**

   If it grows, separate:

   ```text
   codex.oauth          ; PKCE and device flow
   codex.account        ; usage/info operations
   codex.cli            ; prompting and command dispatch
   ```

8. **Minor cleanup**
   - `io.github.jolt-lang/time` appears unused by project source.
   - `codex.ws/pool` appears unused by the application.
   - `README.md` does not list `codex.schema` in its architecture bullets.
   - `docs/SOL-REVIEW.md` still reports 25 tests / 78 assertions.
   - CI loads some namespaces only transitively; `codex.schema` and both transport namespaces should be explicit if the step claims to load every production namespace.

# Libraries suitable for this project

## 1. Jolt `clojure.tools.logging` port — strong recommendation

The official Jolt Ring example uses:

```clojure
org.clojure/tools.logging
{:git/url "https://github.com/jolt-lang/logging"
 :git/sha "..."}
```

This directly addresses the remaining scattered `println` calls.

Recommended structured context:

```clojure
(log/warn {:event :ws-fallback
           :request-id request-id
           :session-hash session-hash
           :error-type (:type (ex-data error))})
```

Never include tokens, prompts, authorization headers, raw session identifiers, OAuth codes, or arbitrary upstream bodies.

This is the most immediately valuable new library.

## 2. `clojure.test.check` and Malli generators — strong test-only fit

Malli already resolves `test.check` transitively, and `malli.generator/generate` works on Jolt. If tests start using it, declare it explicitly under `:test` rather than relying on an incidental transitive dependency.

Good properties:

- WS frame encode/decode round trips.
- Fragmented input never exceeds the aggregate cap.
- Continuation delta never introduces old input items.
- Normalization is idempotent.
- Responses unknown top-level fields survive preparation unchanged.
- Generated schema-valid requests do not fail structural translation.
- Invalid session characters are always rejected.

This offers much more value than introducing a heavier test runner.

## 3. Malli’s existing adjacent modules — useful without another dependency

Already verified on Jolt:

- `malli.error/humanize`
- `malli.generator`
- `malli.json-schema`
- `malli.swagger`
- `malli.transform`

Potential uses:

- Generate a compatibility-oriented request-schema document.
- Produce fixtures and fuzz inputs.
- Validate internal event-source metadata in development.
- Validate application configuration.

Avoid request coercion with `string-transformer`; strict JSON wire types are preferable for this proxy.

## 4. Integrant — suitable only if lifecycle resources grow

Integrant is verified by Jolt’s official Ring example. It becomes useful if the service gains several independently restartable resources:

- HTTP server;
- WS session pool;
- token store;
- periodic sweeper;
- metrics server;
- configuration watcher;
- SQLite store.

The present `start!`/`stop!` implementation is smaller and easier to audit. Adding Integrant now would mostly replace 50 lines of explicit lifecycle code with framework configuration, so I would defer it.

## 5. Reitit — defer for the current four routes

Reitit works in the official Jolt Ring stack with `jolt-lang/router`, which supplies the required trie implementation.

It would become appropriate for:

- many endpoints;
- path/query parameters;
- route-level middleware;
- generated endpoint metadata;
- versioned APIs;
- an administrative API.

For four exact method/path matches, the current `cond` is clearer and has fewer dependencies.

## 6. `crypto-equality` — optional

The Jolt Ring example verifies `crypto-equality`. It could replace the manual length check plus `java.util.Arrays/equals` API-key comparison.

The existing implementation is compact and already timing-resistant enough for this boundary, so adding a dependency solely for one comparison is not compelling. It makes more sense if additional secret comparisons appear.

## 7. Ring middleware — add selectively, not as `ring-defaults`

Useful possibilities:

- request IDs;
- sanitized exception mapping;
- security headers;
- access logging;
- origin checks.

`ring-defaults` is verified on Jolt but primarily targets browser applications with sessions, cookies, forms, static resources, and CSRF protection. Much of that is irrelevant to a JSON/SSE proxy and could complicate streaming. Small custom Ring middleware is preferable here.

## 8. Jolt nREPL/CIDER middleware — good development-only addition

The official example uses `jolt-lang/nrepl` for editor completions, lookup, test operations, and interruptible evaluation. This belongs in a development alias, not runtime dependencies.

It would improve the stated REPL-driven workflow, provided a full pinned SHA is used.

## 9. `clojure.tools.cli` — only if CLI options expand

The current command dispatch is intentionally tiny. A CLI parser becomes useful for options such as:

```text
serve --port ...
info --full
login --device
usage --json
```

Jolt compatibility should be probed before adoption; unlike Integrant/Reitit/logging, it is not demonstrated by the examples inspected here.

# Tools suitable for the repository

## `clj-kondo`

Useful as a source-analysis CI step, with caveats:

- It analyzes Clojure semantics rather than Jolt runtime behavior.
- Jolt FFI macros and Java shim classes may need configuration or hooks.
- Warnings involving JVM reflection or unsupported Java classes must be reviewed, not blindly enforced.

Start with a narrow rule set: unused bindings/requires, malformed destructuring, shadowing, arity errors, and suspicious namespace references.

## Formatter: `zprint`, `cljfmt`, or `cljstyle`

Use as an external source tool rather than a runtime dependency. First run it in check-only mode because automatic formatting may fight intentionally aligned protocol code and Jolt-specific forms.

`brepl balance` should remain mandatory for `.clj` edits; a formatter does not replace reader/balance validation.

## Generic CI tools

These do not depend on Jolt and fit the security profile:

- `gitleaks` for credential/token patterns.
- ShellCheck for future packaging scripts.
- Dependency-SHA update script with a test gate.
- Standalone `jolt build` smoke test if binary distribution is intended.
- A separate opt-in live-backend test workflow with no credentials on pull requests.

Kaocha, Eastwood, JVM clojure-lsp execution, and Java coverage agents should not be assumed to run under Jolt.

# Libraries for adjacent Jolt applications

The official Jolt examples demonstrate a surprisingly broad conventional Clojure stack.

## Larger web applications

| Concern | Suitable stack |
|---|---|
| HTTP | `ring-chez-adapter` |
| Routing | Reitit + `jolt-lang/router` |
| Middleware | Ring Core / Ring Defaults |
| Lifecycle | Integrant |
| Logging | Jolt `clojure.tools.logging` port |
| Templates | Selmer or Hiccup |
| Forms/uploads | `ring-codec`, `jolt-lang/multipart` |
| Validation | Malli |
| Time | Tick through `jolt-lang/time` |
| SQL construction | HoneySQL |
| Database | `jolt-lang/db` over native SQLite |

This would fit dashboards, small internal services, CRUD systems, local-first servers, webhook receivers, and administrative tools.

## Persistent proxy/gateway variants

If this application evolved to retain audit or quota state:

- `jolt-lang/db` + SQLite for session metadata, rate counters, or resumable jobs.
- HoneySQL for query construction.
- Integrant for DB and sweeper lifecycle.
- Malli for stored-record and configuration validation.

Avoid storing prompts or model outputs by default; that materially changes the privacy and threat model.

## HTML and content applications

Verified options:

- Hiccup for HTML as data.
- Selmer for file-based templates.
- `markdown-clj`, with its documented Jolt shim/metadata limitations.
- The dependency-free CommonMark example for a deliberately constrained renderer.

Suitable for documentation servers, static-site generators, email rendering, reports, and OAuth callback pages more complex than this proxy needs.

## Interactive/server-driven applications

Jolt examples include:

- Glimmer with GTK4 for desktop applications.
- Glimmer TUI for terminal applications.
- Glimmer + Datastar for reactive server-rendered web interfaces.

These are attractive for local account managers, proxy monitors, usage dashboards, or developer tools, but are younger and more Jolt-specific than Ring/Malli/Integrant.

## DSLs and developer tools

- Malli for declarative data languages.
- `clojure.edn` for trusted configuration.
- Edamame for richer Clojure/EDN parsing where reader control is needed.
- Hiccup for generated reports.
- `test.check` for compiler/parser/property testing.

`rewrite-clj` may be relevant to source transformation tools but should be explicitly tested on Jolt before commitment.

# Familiar JVM choices that should generally be avoided

These rely heavily on Java bytecode, NIO, classloading, or JVM frameworks:

- Jetty, Undertow, http-kit, Aleph/Manifold.
- Jackson-backed Jsonista and Cheshire.
- `next.jdbc`, HikariCP, JDBC drivers.
- Kafka’s Java client and most Java database clients.
- Logback, SLF4J backends, Java OpenTelemetry agents.
- JVM cryptography libraries such as Bouncy Castle/Buddy stacks without a Jolt-specific port.
- Java CommonMark implementations.
- Java test/coverage runners.

Prefer pure Clojure, `.cljc`, Jolt ports, or native libraries exposed through `jolt.ffi`.

## Recommended order

1. Add the Jolt logging port and central error/log redaction.
2. Add direct WS frame/pool tests, using `test.check` where beneficial.
3. Inject clock/random dependencies into protocol and expiry code.
4. Split `codex.ws` only while adding those tests.
5. Remove unused `jolt-lang/time` and global `codex.ws/pool` after confirmation.
6. Add clj-kondo and formatter check-only CI.
7. Adopt Integrant/Reitit only if the service gains materially more resources or routes.

The key conclusion is that the architecture is already appropriately lightweight. Logging, error taxonomy, and protocol testing offer substantially more value than adding a general application framework now.
